## Zone gotchas (facts not in the root docs)

1. **All commands run in the php-fpm container** — `backend/Makefile` wraps `docker compose exec`. `composer`/`php bin/console` on the host fail.
2. **CS-Fixer rule set** is `@Symfony` + `@Symfony:risky` + `@PHP84Migration` + `@PHP80Migration:risky` (see `.php-cs-fixer.dist.php` — the canonical source).
3. **Entities use string UUIDs** (no auto-increment) and scalar FK columns (`clubId`, `seasonId`… as strings, no object associations). ⚠ Une exception : `PriorityTier` porte un **`id` entier posé à la main** (S…D), ni UUID ni auto-increment.
4. **`declare(strict_types=1)`** in every file; single-action controllers use `#[AsController]` + `__invoke()`.
5. **Redis lock** `ClubGenerationLock` (SETEX NX + release token) serialises generation per club.
6. **Cache pool `cache.schedule`** — dedicated Redis pool for engine payloads, TTL 4h, invalidated by `CacheInvalidationListener` (`src/EventListener/CacheInvalidationListener.php`, hooks Doctrine ORM's `postPersist`/`postUpdate`/`postRemove` only). ⚠ **A raw SQL write (`dbalExec`, a manual `UPDATE`/console `dbal:run-sql`) bypasses it entirely** — nothing invalidates the pool — so purge it by hand (`bin/console cache:pool:clear cache.schedule`) before a generation that must see the change (constaté P4-176, 2026-09-05).
7. **Slot lock levels** = `NONE` / `HARD` only. `SOFT` is **rejected** at the manual-edit lock endpoint (ENG-21): the engine never consumed a soft-lock penalty, so a SOFT lock had zero placement effect — no such no-op weight is built or sent.
8. **Test DB required** before PHPUnit: `make db-init-test` once, then `make phpunit` (`--group phase1`).
9. **Stuck-schedule watchdog** `app:schedules:reconcile-stuck` (BCK-01) — **déjà automatisé, rien à câbler à la main** : entrée `reconcile-stuck-schedules` du `AdminJobCatalog`, **toutes les 10 min** avec `--older-than=60`, déclenchée par le tick `app:jobs:run-due` du `cron-runner`. Elle fait échouer les plannings `GENERATING` abandonnés par un worker crashé/OOM. Terminal-status nets are detailed in root `docs/project-map.md` §2.4.
9b. **Period reminders** `app:periods:remind` (cockpit palier C) — **déjà automatisé** : entrée `period-reminders` du `AdminJobCatalog`, **quotidienne à 08:00** (`app:jobs:run-due`). Elle emails a club's managers (owner+admin) when a period starts within 14 days and still has NO overlay plan. It scans a **[today, today+14] window** and picks the milestone **bucket** (14/7/3 days) — a window (not an exact date) so a **missed run catches up**. Idempotence via `period_reminder_log` (one row per `(calendar_entry_id, threshold)`, global table, no RLS) — never re-sends a milestone. Exits **non-zero if any email fails to DISPATCH** (since P5-3a all app emails route through the Messenger bus — `messenger.yaml` routes `SendEmailMessage` to `async`, the worker performs the SMTP send ; an SMTP outage no longer surfaces here, it lands in the failure transport, visible in the SA console). Never auto-acts (mirrors the in-app radar). Needs `FRONTEND_BASE_URL` (empty → omits the link). `--dry-run` / `--date=YYYY-MM-DD` (strict, rejects rollovers) for rehearsal. Club-walk + per-club GUC like the BCK-01 watchdog; managers via `ClubUserRepository::findManagementEmails` (raw DBAL, empty-GUC safe).
10. **Dated constraints excluded from generation** — a `Constraint` with `calendarEntryId` set belongs to a `CalendarEntry` period (cockpit, palier A) and MUST NOT feed base-plan generation. Generation/validation/report load constraints via `ConstraintRepository::findPermanentByClubSeason` (`calendarEntryId IS NULL`), never `findByClubSeason`. See `specs/courantes/accueil-cockpit-temporel.md` §9ter.
11. **Cockpit unlock** — the SEASON plan carries at least one finished version (`hasFinishedVersion`, exposed on `/api/me` inside `seasonPlan`). It is **derived, never stamped**, and **independent of the pointer**: reopening does not re-lock the cockpit (ADR-0002 inv. 8/16). Gates the frontend cockpit vs work-loop. **ADR-0002 inv. 1**: validating a version = its plan **POINTS** at it (`schedule_plan.chosen_schedule_id`) and its sibling versions of the same scope are **DELETED** (no `ARCHIVED` status, no net); a sibling PENDING/GENERATING blocks the validation (409), and DELETE refuses an in-flight schedule (409). "Validated" is **not a status** — it is derived from the pointer, and a chosen version stays `COMPLETED`. The **name** belongs to the plan (inv. 12), renamed via `PUT /api/schedule_plans/{id}` (SEC-07). **D2**: every season-plan generation also captures a `ScheduleStructureSnapshot` (faithful, generic ClassMetadata serialization of teams/venues/slots/coaches/links/permanent constraints/base reservations — NOT the solver payload) via `StructureSnapshotter` in `GenerateScheduleHandler` (non-fatal); one row per schedule, replaced on regeneration, purged with the schedule artifacts (`OverlayManager`) and by `SeasonDataPurger`. Enables the D3 restore. **D3**: `POST /api/schedules/{id}/regenerate-from` (`RegenerateFromVersionController`) → `StructureRestorer` wipes the current permanent structure (NOT schedules/versions, NOT the calendar/dated rows) and re-inserts the version's photo rows WITH their original ids (graph stays consistent; generic ClassMetadata hydration, symmetric to the snapshotter; `clear()` after the bulk-DQL wipe avoids identity collisions), then queues a fresh generation → a new LINEAR version. See `docs/architecture/adr-0002-pattern-plan.md` + `specs/courantes/planning-lifecycle-validated.md`. Guarded by `ValidateScheduleTest` + `ScheduleLifecycleGuardTest` + `StructureSnapshotterTest` + `StructureRestorerTest` + `RegenerateFromVersionTest`.
12. **School holidays = global reference** — `school_holiday_period` has **no club_id / no RLS** (public national data, like `sport`). Two feeders, both idempotent by `(zone, holidayType, schoolYear)`: **(a)** `app:school-holidays:import` — pulls the official Éducation nationale ODS API (`data.education.gouv.fr`, dataset `fr-en-calendrier-scolaire`), current season + N+1, for **all 13 zones** (A/B/C, CORSE, DOM/TOM); **(b)** `app:school-holidays:seed` — offline JSON fallback (`data/school-holidays.fr-metropole.json`), **no network**. Import rules (`FrenchSchoolCalendarMapper`): filter `population="-"` (term vacations) or `"Élèves"` (summer, drops the `Enseignants` split); a record is a vacation iff **> 3 business days (Mon–Fri) AND label ≠ `Pont …`** (excludes ponts/short breaks/1-day markers); `holidayType` is an **open slug** derived from the label (métropole + overseas differ: `carnaval`, `ete_austral`, `apres_1ere_periode`…). Read via `GET /api/school-holidays` (filtered by the club's `schoolZone` + a window). `Club.schoolZone` is derived from the FFBB code by `SchoolZoneResolver` at register (`app:clubs:backfill-school-zone` for existing clubs, dry-run by default). FFBB code = **3-letter league + 4-digit zero-padded department + sequence**; department → one of the **13 codes** in `SchoolZoneResolver::ZONES` (e.g. `GES0067060` → 67 → `B`; `COR0020001`/`2A`/`2B` → `CORSE`; `GUY0973021` → 973 → `GUYANE`; 971–988 → territory). Unknown shapes / territories not in the map → null → manually editable `schoolZone`. **A second global reference `public_holiday`** (same no-club_id / no-RLS shape) holds jours fériés, fed by `app:public-holidays:import` from the etalab API (`calendrier.api.gouv.fr/jours-feries/{zone}.json`, 10 files, current calendar year + N+1): `zone='NATIONAL'` for métropole fériés (all clubs) + territory extras = **diff territoire − métropole** tagged with the DOM/TOM zone codes (`PublicHolidayMapper`, e.g. Abolition de l'esclavage → GUADELOUPE). `NATIONAL` is a synthetic marker, **not** in `ZONES`. Column is `holiday_date` (`date` is reserved). Read via `GET /api/public-holidays` (NATIONAL ∪ `Club.schoolZone`; null zone still returns NATIONAL). **Display-only — never feeds the solver.** Alsace-Moselle + Saint-Barthélemy/Saint-Martin intentionally not imported.
13. **Cockpit conflicts** — `GET /api/calendar-entries/{id}/conflicts`: for a period entry, reads its closed venues from dated FACILITY constraints, then the **chosen version of the SEASON plan** (`SchedulePlanProvisioner::chosenOfSeasonPlan`) — its slot templates on those venues whose ISO weekday (`ScheduleSlotTemplate.dayOfWeek` = **1=Mon..7=Sun**) falls in the window → returns concrete conflicting dates. Palier A **surfaces** conflicts, moves nothing (overlay = palier B).
14. **Period overlays (palier B)** — a `Schedule` with `calendarEntryId` set is the OVERLAY of a period. ⚠ There is **no** inverse pointer on the entry: `CalendarEntry.overlayScheduleId` was **dropped** (ADR-0002 lot D-b, 2026-07-18) — "which version is active for this period" derives from its plan (`SchedulePlanProvisioner::chosenOfPeriodPlan`). ⚠ **#8 (fondateur 2026-07-24) — la période POSSÈDE sa grille.** Les `VenueTrainingSlot` d'une période sont une **copie** du modèle de saison prise à la naissance du plan et ancrée par **`schedulePlanId`** (plus par `calendarEntryId` — l'ancre est le PLAN, car la découpe hebdomadaire donne 2 plans sur un même déclencheur calendrier). `buildForOverlay` lit **cette grille-là et elle seule — JAMAIS d'union avec les créneaux de saison** : un gymnase n'a donc jamais deux jeux de créneaux dans une période, rien ne se chevauche entre couches et aucun verrou n'est ambigu. Réglages **sparses** ancrés au plan (pas de ligne = hériter) : `VenuePeriodOverride` + enum `VenuePeriodMode` (`DISABLED` = le gymnase ne sert pas du tout cette période et **sort entièrement du payload** — sinon toute contrainte le nommant deviendrait un id fantôme ; `BLANK` = grille vierge ; **`INHERIT` n'est jamais stocké**, revenir au défaut = SUPPRIMER l'override — `mode` est désormais **nullable**, une ligne peut n'exister que pour son masque), `TeamPeriodOverride` (`isActive`, `sessionsPerWeek`), `ConstraintPeriodOverride` (`isActive`). ⚠ **Indisponibilité INFORMATIVE (décision fondateur 2026-08-18)** : `VenuePeriodOverride` gagne un masque manuel `dayOverrides` (jour ISO 1..7 → `VenueDayState::OPEN`\|`CLOSED`) qui s'AJOUTE au défaut dérivé d'une fermeture datée (`venue_closed`) — composition faite UNE fois, dans `App\Service\PlanVenueClosures::effectiveStateForPlan/Entry`, jamais redérivée ailleurs. **`OrphanPinGuard`** : refaire cette grille peut laisser un verrou work-loop ou une réservation qui ne correspond plus à aucun créneau — la génération est alors **refusée en 422** avec un message nommant le gymnase et le jour (`GenerateScheduleController`), au grain de l'état EFFECTIF ci-dessus. Pas de filtrage silencieux : « on ne fait pas de chose magique, on voit et on informe le gestionnaire » — c'est lui qui redéfinit ses créneaux ou retire l'épinglage. Ne concerne QUE les plannings de période (le socle définit lui-même sa grille). ⚠ **P2-9ter (2026-07-31) — `buildForOverlay` n'est plus qu'un ADAPTATEUR** sur `buildForPeriodPlan(clubId, seasonId, schedulePlanId, entry, solverSeed, ?scheduleId)` : le `Schedule` n'apportait que ces cinq scalaires. Le chemin scalaire permet de calculer le payload d'une période **AVANT toute génération** (`scheduleId` null ⇒ aucun `ScheduleSlotTemplate`, ce qui est juste : les verrous durables sont les `Reservation`, portées par le plan). Il n'existe **qu'un seul** chemin de calcul, gardé par un test de parité — trois tentatives d'en recopier la logique à la main ont divergé. Corollaire : **construire un payload n'écrit plus rien** (l'appel à `TeamTagService::syncTeamTags` a quitté `serializeTeam` ; les tags sont LUS, et maintenus par `TeamTagSyncListener`). Generation branches on it: `GenerateScheduleHandler` calls `ScheduleConstraintBuilder::buildForOverlay` (closure = ALL permanents kept by default + dated ; **holiday/reprise = permanents inherited with a SMART default that follows the team selection** — CLUB/COACH kept, TEAM kept iff its team reprend, FACILITY dropped — via `activePermanentForReprise` + dated ; a period toggle is a sparse `ConstraintPeriodOverride` deviation ; a TEAM constraint for a deactivated team never ships), which **BYPASSES the schedule-input cache**. Generating never points a plan at anything (ADR-0002 inv. 2 — no auto-pointing; only the manager chooses). Deletion of an overlay/period goes through `OverlayManager` (diagnostics have no FK cascade — purge them ; **depuis P4-30 `reservation.schedule_plan_id` et `venue_training_slot.schedule_plan_id` portent, eux, une FK `ON DELETE CASCADE` vers `schedule_plan`** — supprimer un plan emporte donc ses lignes ancrées côté BASE, sans purge PHP). ⚠ **`config.type=venue_closed` (the dated constraint the cockpit creates) is a NO-OP in the engine** — since 5b (#263) `buildForOverlay` **removes the closed venue's training slots from the payload on its actually-closed weekdays** (`App\Service\VenueClosureDays`, incident ∩ window — the old all-days per-team `forbiddenVenueId` expansion is gone; over-closes on the whole block if a weekday repeats, never under-closes). If the dated constraint ever needs to be consumed as-is → engine change → re-validate with the user.
15. **Destructive reopen of the season calendar** — reopening (= un-pointing, inv. 2) the SEASON plan's **chosen version** while overlays exist → **409 `{code:"overlays_exist", count, overlays[]}`**; the client re-POSTs `{"confirmDeleteOverlays": true}` → `OverlayManager` deletes the overlays (entries + dated constraints KEPT — the period falls back to "signalée"). Guarded by `ReopenScheduleTest`.
16. **Interlinked-entity cascade delete** — ⚠ **Avant toute cascade, le périmètre engagé (P2-7a)** : `TeamEngagementGuard` refuse en **409** la suppression **ET** le changement de `level` d'une équipe portant **au moins un match, quel que soit son statut** — l'import FBI crée tout en `UNPLACED`, donc une garde qui exigerait `PLACED` serait inerte au moment précis où elle doit mordre. Ses matchs sont déposés à la fédération : on ne revient plus dessus. Restent **libres** : `priorityTierId`/`tierOrder` (la perception du club, ça bouge) et `isActive` (qui sert aux plannings de période, pas au périmètre de la saison). `isEngaged()` et `engagedTeamIds()` répondent à la MÊME question — garde d'écriture et contrat de lecture — et doivent le rester. Ensuite seulement : team/venue/coach/availability-slot rows carry **no ORM association** and, à deux exceptions près, **no DB FK** (all links are plain guid columns). ⚠ Les exceptions, posées à la main en migration et INVISIBLES de Doctrine (donc `migration-diff` propose de les DROPper — ne jamais committer ce DROP) : `reservation.schedule_plan_id` et `venue_training_slot.schedule_plan_id` → `schedule_plan` en `ON DELETE CASCADE` (P4-30, gardé par `SchedulePlanAnchorCascadeTest`), et les deux FK de `coach_wish_token`. Cette cascade s'exécute en owner, donc **exemptée de RLS** — c'est ce qui garantit qu'aucun orphelin ne survit, so a bare `remove()` orphans reservations, coach links, constraints and the materialised HARD `ScheduleSlotTemplate` the solver reads back — an **orphan reservation still forces a phantom HARD pre-placement**. `EntityCascadeDeleter` (called from each `*StateProcessor` via the `AbstractStateProcessor::cascadeBeforeDelete` hook) purges the deleted row's logical children — **team** → reservations · team_coach · coach_player · slot_templates · scoped constraints · tag assignments · **fixtures · competitions · schedule_diagnostics** ; **venue** → slots · reservations · templates · diagnostics · FACILITY constraints · null-out `forcedVenueId`/`fixture.venueId` ; **coach** → team_coach · coach_player · diagnostics · COACH constraints · null-out `template.coachId` ; **slot** → its reservations + only their **HARD** templates (SOFT/NONE solver results on the same venue/day/time are RESULTS, not pins — never touched). Scoped by `clubId + seasonId` **and** RLS (never crosses a club). Filters disabled via the `DisablesTenantFilters` trait (shared with `SeasonDataPurger`/`PurgeOrphansCommand`) — the reserved-word `constraint` table breaks their alias; NOT re-enabled (Doctrine drops a disabled filter's bound params, and the DELETE 204 needs no further scoped read). `app:purge-orphans` (`--force`) one-shot-cleans orphans left by pre-cascade deletes (orphan reservations, dangling links, HARD templates whose slot/team is gone, constraints whose scopeTargetId is gone). ⚠ **Known gap**: a constraint that references a deleted entity only inside its `config` JSON (multi-target family) or via `parentConstraintId` is NOT cleaned — scope+scopeTargetId only. Guarded by `CascadeDeleteApiTest` (§7.1: cascade completeness + tenant isolation with a shared-teamId cross-club case).
17. **Stale Symfony cache under the WSL2 bind-mount** — the dev container may not see host file mtimes, so the serializer/metadata cache survives a pull that changed `src/ApiResource`/`src/Dto` (symptom 2026-07-23: `parentEntryId` silently missing from every `application/json` response while jsonld had it). After a pull touching those dirs, run `bin/console cache:clear` in php-fpm. ⚠ **Opcache sits ABOVE that cache**: regenerating `specs/courantes/openapi-snapshot.json` re-exported a stale docblock even though the container `grep`ed the new file and `cache:clear` had run — `docker compose restart php-fpm` before `api:openapi:export`. Related: `skip_null_values: false` in `config/packages/api_platform.yaml` keeps null keys PRESENT in `application/json` (the frontend compares with strict `null ===`) — guarded by `JsonNullKeysTest` (phase1).
18. **Doléances coachs (#10) — LA SEULE ROUTE `/api/*` NON AUTHENTIFIÉE.** `GET|POST /api/coach-wishes/public/{token}` (`PublicCoachWishController`) : le coach ouvre son lien personnel, **sans login** — le `CoachWishToken` porte à lui seul l'identité, le club et le périmètre. Le token est stocké **EN CLAIR** en base (c'est un lien envoyé par email, pas un secret d'authentification). Défenses, toutes load-bearing : route `PUBLIC_ACCESS` donc **jamais de 401** (le client ky redirige vers `/login` sur 401) ; **rate-limit PAR IP AVANT tout lookup** (`coachWishPublicLimiter` → **429**), GET compris car le pré-remplissage est énumérable ; forme du token validée puis **404 BYTE-IDENTIQUE** pour inconnu et malformé (anti-énumération) ; deadline dépassée ou saison en lecture seule → **410** (l'extension côté gestionnaire ranime le lien) ; écriture **bornée au périmètre du token** (ce coach, ses équipes ∩ campagne, les semaines de la campagne) — une seule violation → 422 et **RIEN d'écrit**. **RLS hybride** : le GUC `app.club_id` est posé **depuis le token** avant toute écriture et **TOUJOURS relâché en `finally`** (patron `verifyEmail`). Le read-only de saison a **une seule source**, `CoachWishSeasonGuard` (dérivé du calendrier, pivot 15-juillet — PAS du statut `archived`), partagée par le 410 public et le 409 des actions management : deux copies avaient déjà divergé. Entités `CoachWish` / `CoachWishCampaign` / `CoachWishToken` ; digest quotidien `app:coach-wishes:digest`.
19b. **`BaseContext::dbalScalar` (Behat)** — sur un `SELECT` sans ligne, `dbal:run-sql` imprime « [OK] … empty result set » et cette ligne n'est filtrée par aucun garde du parseur : elle revient telle quelle au lieu de `''`. Préférer `COUNT(*)` (toujours une ligne) à un `SELECT` nu quand un context Behat vérifie une absence.
19. **Trois refus SYNCHRONES avant toute mise en file** sur `POST /api/schedules/{id}/generate` (`GenerateScheduleController`, avant le dispatch Messenger) : **409** si la version est celle que son plan **pointe** (il faut la rouvrir d'abord — ADR-0002 inv. 1) ; **422** si `GenerationComplexityGuard` juge le problème hors bornes (A10, garde anti-« generation bomb » : plafonds généreux, ~10× un gros club FFBB, alignés sur ce que le payload porte réellement — contraintes comptées **permanentes only**) ; **422** si `OrphanPinGuard` trouve un épinglage orphelin (gotcha 14). Aucun de ces trois ne crée de `Schedule` en `PENDING` ni de diagnostic : l'appelant reçoit l'erreur tout de suite.
